## Быстрый старт {#quick-start}

Dinary — ваш собственный небольшой сервер, а приложение на телефоне — страница,
которую он отдаёт. Он бесплатно работает на виртуалке Oracle Cloud Always Free и
доступен через вашу приватную сеть Tailscale.

=== "С ИИ-агентом"

    Есть подписка Claude Pro или Max либо ChatGPT Plus? Откройте вкладку **Code**
    в настольном приложении Claude или **Codex** в настольном приложении ChatGPT
    и вставьте:

    ```text
    Установи мне dinary на Oracle Cloud по инструкции
    https://andgineer.github.io/dinary/agent-install/
    ```

    Агент по шагам скажет, что можете сделать только вы, — зарегистрироваться в
    Oracle и Tailscale, вписать ключ в файл, — а остальное сделает сам.

=== "Вручную"

    1. Разверните сервер:
          - [Oracle Cloud Free Tier](deploy-oracle.md) — $0/месяц навсегда
          - [Свой компьютер](deploy-selfhost.md) — $0 (Tailscale Funnel или Cloudflare Tunnel)
    2. Настройте HTTPS-доступ — см. инструкции по деплою выше.
    3. [Установите PWA](pwa-install.md) на телефон.
    4. Первоначально загружается [классификатор](taxonomy.md), который вы далее можете
       корректировать.
    5. При желании [настройте Google Sheets](google-sheets-setup.md), чтобы каждый
       расход попадал строкой в таблицу.
    6. Запустите `inv analytics` — своего [персонального финансового аналитика](analytics.md).

## Что умеет {#what-it-does}

Dinary server — бэкенд на FastAPI, который:

- Хранит расходы в локальной SQLite-базе (в EUR, с исходной суммой и валютой для аудита)
- Опционально дублирует каждый расход в Google Sheets (конвертируя в RSD для сводной таблицы)
- Парсит QR-коды сербских фискальных чеков (сумма + дата)
- Раздаёт мобильное PWA-приложение для быстрого ввода расходов в динарах
- Поддерживает офлайн-очередь записей при отсутствии связи

## Как это устроено {#under-the-hood}

**Исправления становятся правилами.** Известные позиции классифицируются по
сохранённым правилам, незнакомые и сомнительные уходят в LLM. Исправление
пользователя важнее модели и действует во всех магазинах той же сети. Сбои
классификации остаются исправимыми: есть повторы и ручной разбор.
[Дизайн классификации](https://github.com/andgineer/dinary/blob/main/specs/reference/classification-pipeline.md) объясняет уверенность,
альтернативы и ручное разрешение.

Выбор провайдера и переключение между провайдерами берёт на себя
[llmbroker](https://github.com/andgineer/llmbroker) — отдельная библиотека для
приложений, которым нужен пул LLM-провайдеров. Логика чеков остаётся в Dinary.

**Сохранённый расход переживает упавший сетевой запрос.** Офлайн-записи хранятся
в IndexedDB, а сканер QR встроен в приложение и работает без сети. На сервере
источник истины — SQLite-журнал. Выгрузка в Google Sheets идёт через очередь с
повторами, так что недоступная таблица не мешает записывать расходы. См.
[офлайн-дизайн](https://github.com/andgineer/dinary/blob/main/specs/reference/pwa-offline.md) и [интеграцию с Sheets](https://github.com/andgineer/dinary/blob/main/specs/reference/sheets.md).

**У аналитики свой дом.** Локальное приложение аналитики через DuckDB читает
реплику журнала только для чтения, поэтому тяжёлые аналитические зависимости не
попадают на сервер. Его AI может запрашивать траты и настраивать представления,
не меняя журнал. [Дизайн аналитики](https://github.com/andgineer/dinary/blob/main/specs/reference/analytics-ai.md) описывает дашборд и
MCP-интерфейс.

**Хранилище определили частые мелкие запросы.** В раннем синтетическом тесте
5 000 обращений к таблице соответствий заняли 2,0 секунды на прямом SQL и
19,9 секунды через Ibis. Поэтому транзакционный бэкенд построен на SQL-файлах и
миграциях. [Архитектурная запись](https://github.com/andgineer/dinary/blob/main/specs/reference/architecture.md#sql-files-over-ibis)
описывает нагрузку и компромиссы; результат относится к этому замеру, а не к
скорости всего приложения.
